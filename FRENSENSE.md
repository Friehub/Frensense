# Frensense: The Semantic Diagnostic Engine

**Formerly known as GenSense.**

---

## The Problem

Modern software quality tools are stuck at the syntactic layer. `rustfmt` formats code. `clippy` checks patterns. `eslint` enforces style. TypeScript's type system enforces type correctness. These tools are excellent at what they do — but they all operate on the same plane: *does this code conform to a set of mechanical rules?*

They cannot answer the harder question: *does this code do what the developer intended?*

This gap is not academic. It shows up in production:

- A function named `validate()` that always returns `true` because the rejection path was never implemented. It compiles. It type-checks. The linter passes. It ships.
- An async block that acquires a `std::sync::Mutex` guard, then `await`s a future. This is a textbook deadlock in Rust. No linter catches it because it requires reasoning about execution order, not just token presence.
- A `sanitize()` function that was written to strip dangerous characters but, after a refactor, passes its input through unchanged. Every downstream consumer trusts it. No tool flags it because the function signature looks correct.
- A connection opened inside a transaction scope and never released. The connection pool exhausts under load. The unit tests pass.
- A tRPC mutation with no auth check. The route is live. The omission is invisible to the type system.
- AI-generated code with an assertion that is structurally valid but always evaluates to `true`. It was generated by an LLM that filled in a plausible-looking condition. No one noticed.
- A `todo!()` or `unimplemented!()` on a reachable production path that was committed months ago and forgotten.

**The conventional linter cannot detect any of these.** They all require understanding semantic intent — the relationship between what code says and what it is supposed to do.

This is the problem Frensense was built to solve.

---

## What Frensense Is

Frensense is a semantic diagnostic engine for **Rust** and **TypeScript**. It operates one level above the type system, using a multi-pass analysis pipeline to surface code that is syntactically and type-theoretically correct but semantically broken.

It is not a linter. It is not a fuzzer. It is not a formal verifier. It is a static analysis engine focused on the class of bugs that fall between what the compiler checks and what the developer intended.

---

## How It Works

### The Multi-Pass Pipeline

When Frensense scans a project, it runs a structured pipeline before executing any rule:

**Pass 1: Symbol Discovery**
All named functions, variables, types, constants, and module-level definitions are extracted into a symbol table. This gives every subsequent pass a complete picture of the project's vocabulary.

**Pass 2: Call Edge Discovery**
Function call relationships are mapped across files into the `SemanticGraph`. This enables cross-file reasoning — a rule can ask "does any caller of this function pass untrusted input?" without being confined to a single file.

**Pass 3: Event Discovery**
Inside each function scope, a temporal event chain is constructed: acquire events (lock acquisition, connection open, resource allocation), await events, release events (drop, close, return). This temporal model is what enables detection of the mutex-then-await deadlock pattern and connection leaks.

**Pass 4: SPG Assembly**
The Symbol table, call graph, and event chains are assembled into the **Semantic Program Graph (SPG)**. Every rule receives the full SPG as context alongside the AST node it is evaluating. This is the architectural decision that makes cross-cutting queries possible.

**Pass 5: Rule Execution**
All active rules run against each file. Rules that use algebraic combinators (`AllOf`, `AnyOf`, `Not`, `Across`, `Without`, `Chain`) are evaluated via a recursive tree-walk evaluator against the SPG.

After rule execution, taint flows are materialized as `TaintFlow` edges in the graph, allowing compound rules that combine taint, temporal, and scope constraints.

---

### The Semantic Program Graph (SPG)

The SPG is the core data structure that distinguishes Frensense from a conventional linter. It is not just an AST. It is a multi-dimensional graph that encodes:

- **Symbol relationships**: what calls what, what imports what.
- **Temporal ordering**: the sequence of significant events within a function's execution path.
- **Taint flows**: how untrusted data travels through the codebase.
- **Scope boundaries**: what is internal, what is public-facing, what crosses a trust boundary.

Rules query this graph using a structured predicate API. A rule can express: "flag any function that acquires a lock, then reaches an await point, without releasing the lock in between." This is a temporal constraint on a graph — not a pattern match on text.

---

### Taint Analysis

Frensense tracks how data flows from untrusted sources (HTTP request bodies, environment variables, user input, external API responses) through the program to sensitive sinks (database queries, shell commands, file paths, auth checks).

Taint analysis is:
- **Intra-procedural**: within a single function scope.
- **Inter-procedural**: across function call boundaries, up to a configurable depth (`--taint-max-depth`).
- **Confidence-scored**: each taint flow carries a confidence score based on how directly the source reaches the sink. Low-confidence flows are reported separately.

---

### Algebraic Flow Combinators

Rules are not limited to single-predicate checks. The combinator system allows composing constraints:

- `AllOf`: all sub-conditions must hold.
- `AnyOf`: at least one sub-condition must hold.
- `Not`: the sub-condition must not hold.
- `Across`: the condition holds across a function call boundary.
- `Without`: the condition holds in the absence of an intervening event.
- `Chain`: a sequence of events must occur in order.

These combinators allow expressing rules like: "flag any path that reads from a user-controlled source (`AnyOf` HTTP params, query strings), passes through a function that does not sanitize it (`Without` a sanitize call), and reaches a database write (`Across` a call boundary)." This is a real SQL injection pattern expressed as a compound constraint, not a regex.

---

### Contextual Structural Analysis (CSA)

CSA is a lighter-weight analysis layer for reasoning about function bodies without full data flow analysis:

- `body_must_contain`: the function body must contain a specific pattern. Used to catch `validate()` functions with no rejection path — the body must contain a return of a falsy value or an error variant.
- `body_may_delegate_via`: allows suppression when the function delegates its responsibility to another function. Prevents false positives when validation is done inside a helper.

CSA rules run after the SPG is assembled and have access to the full call graph, but they express their constraints in a simpler predicate language suitable for the majority of semantic checks that do not require full taint tracking.

## The Rule Architecture and Why Embedded Rules Are Being Retired

### Current State (v0.3.x)

Frensense currently ships with 67 embedded rules compiled into the binary, organized into suites (`default`, `extended`, `all`). This was the right approach for getting the engine to a functional state quickly.

The limitation is that **the engine and the policy are coupled**. If a rule needs to change — a threshold adjusted, a pattern refined, a new variant added — a new engine release is required. The rule set cannot be versioned independently.

This also means that teams cannot inspect exactly what rules are running against their codebase without reading Rust source code.

### The Direction: External-Only Rules (v0.4.0)

Starting with v0.4.0, embedded rules will be fully retired. The engine will ship with no built-in rules. All rules are supplied via `--rules-dir`.

This is not a reduction in capability. It is a separation of concerns:

- **The engine** (Frensense binary) handles parsing, graph construction, taint tracking, and rule evaluation. It is versioned on its own cadence.
- **The rule catalogue** (a separate repository) contains the YAML rule definitions. Teams can pin to a specific version of the catalogue independently of the engine version.

This architecture makes the analysis fully auditable. Every rule running against a codebase is a human-readable YAML file checked into version control. There is no hidden policy baked into a binary.

The official Frensense rule catalogue will be published as a standalone repository. Teams can:
- Use the official catalogue as-is.
- Fork it and maintain their own variants.
- Publish their own domain-specific catalogues.
- Mix multiple catalogues using multiple `--rules-dir` arguments.

| Today (v0.3.x) | v0.4.0+ |
| :--- | :--- |
| `frensense . --suite default` | `frensense . --rules-dir /path/to/frensense-rules/default/` |
| `frensense . --suite extended` | `frensense . --rules-dir /path/to/frensense-rules/extended/` |
| `frensense . --suite all` | `frensense . --rules-dir /path/to/frensense-rules/` |

## Why Frensense Will Be Used

### In Solo Engineering Contexts

When building complex systems alone or in small teams, the cognitive overhead of tracking every implicit contract — "this function must never receive untrusted input without prior sanitization," "this lock must always be released before the next await" — is enormous. Frensense externalizes those contracts into machine-checkable rules that run on every commit.

### In AI-Assisted Development

LLMs generate syntactically correct, type-safe code that is often semantically wrong. The patterns Frensense detects — always-true assertions, empty test bodies, sanitize-passthrough functions, missing rejection paths — are exactly the failure modes of AI-generated code. Frensense functions as a semantic post-processor for AI output.

This use case is also why Frensense ships an **MCP server** (Model Context Protocol). An AI agent building a backend system can run Frensense as a tool, receive structured findings, and self-correct before producing output. The agent does not need to understand Rust or TypeScript semantics to benefit from Frensense — it just needs to be able to call a tool and act on JSON findings.

### In CI Pipelines

Frensense is designed for CI integration:

- `--strict` exits with code 1 on any finding.
- `--severity critical` filters to only the highest-severity findings.
- `--diff-only` scans only files changed since the last commit, keeping CI fast.
- `--emit-baseline` and `--compare-baseline` enable regression detection: only new findings since the baseline are reported.
- SARIF output integrates directly with GitHub Advanced Security and similar platforms.

### As Part of the Friehub Stack

Within the broader Friehub engineering stack, Frensense serves as the **semantic quality gate**:

- **Blueprint** generates interface specifications and adapter scaffolding. Frensense verifies that the generated code correctly implements the contract semantics (auth checks present, no passthrough sanitizers, no missing rejection paths).
- **Fwen 14B** generates code from natural language requirements. Frensense runs as a post-generation validator, catching the class of semantic errors that fine-tuning alone cannot eliminate.
- The **Oracle Network** processes on-chain computation in a security-sensitive environment. Frensense enforces the invariants (no secret leaks, no connection pool exhaustion, no auth bypass) that the Rust type system cannot express.

---

## What Frensense Does Not Do

Frensense is a static analysis engine. It does not:

- Run the code (no dynamic analysis).
- Verify mathematical correctness of algorithms.
- Detect runtime race conditions that are not expressible as temporal graph constraints.
- Replace security audits for production systems handling financial or medical data.

It catches the bugs that are detectable from source structure and data flow without execution. For everything else, it surfaces findings that warrant deeper review.

---

## Summary

Frensense was built to close the gap between "the compiler accepts this" and "this does what we intended." It operates on a Semantic Program Graph that encodes symbol relationships, temporal event chains, and taint flows — giving rules a richer context than any conventional linter can provide.

The engine is designed to be fast, composable, and fully auditable. Embedded rules are being retired so that analysis policy and engine mechanics can evolve independently, each versioned and audited on their own terms.

It will be used anywhere code needs to be correct at the level of semantic intent, not just syntactic form.
